# 实测结果汇总（2026-11-05/06）

> 部署模型：自训练 `full_sft_768.pth` → HF（native/HF logits max|diff|=0）→ q3e4（SHA256 feb574f9…，28,632,448 B）
> 设备：ESP32-P4 rev v1.3，360 MHz，16 MB flash / 32 MB PSRAM；板端上下文 192 token，KV FP16（等价 96 FP32 内存）

## 1. 速度与 GEMV 占比（板端实测，3 次运行）

| 指标 | 值 |
|---|---|
| decode（优化后：int16 激活 + 零拷贝打包 GEMV） | **2,639 ms/token（0.379 tok/s）** |
| GEMV 部分 | **2,607 ms/token** |
| **r = GEMV / total** | **0.988** |
| 优化前（标量/展开权重，历史实测） | 5,622 ms/token（0.178 tok/s） |
| kernel-level 加速比 | **2.13×** |
| Amdahl 预测端到端（r=0.988） | 1/(0.012+0.988/2.13) = **1.97×** |
| GEMV 有效权重流量 | 28.63 MB / 2.607 s = **10.98 MB/s** |
| PSRAM 顺序读带宽（/bw 微基准） | 待测 |

**归因结论**：GEMV 占 decode 98.8%；其有效流量仅 ~11 MB/s，远低于 PSRAM 上限 → 瓶颈是 GEMV 内核的**解包 + 标量整数点积指令流**，不是 PSRAM 带宽。

## 1b. Kernel 优化（2026-11-06 凌晨实测）

| 版本 | ms/token | tok/s | gemv ms/token | 相对标量基线 | 相对上一版 |
|---|---|---|---|---|---|
| 标量 / 展开权重（历史） | 5,622 | 0.178 | — | 1× | — |
| int16 激活 + 零拷贝打包 | 2,639 | 0.379 | 2,607 | 2.13× | 1× |
| **+ 激活量化外提 / offset 消除（本轮）** | **2,152** | **0.465** | **2,120** | **2.61×** | **1.226×** |

- 本轮优化内容：lm_head 激活量化从 6400 行重复调用外提为每 token 一次；GEMV 内改为
  Σq·xq（无符号）再减 offset，块内 Σxq 预计算；`-O3` 编译。
- **r（精确口径，含 lm_head）**：**0.985**（GEMV 2,120 ms/token / 总 2,152 ms/token）；\n- **数值等价**：优化后 `/ppl 1` 的 CE 仍为 **6.662094**（与优化前逐位相同）；
  device/host 生成 prefix 29/30 一致。
- **PSRAM 顺序读带宽 `/bw`**：1 MB 顺序读 **95.9 MB/s**（下界，单累加器）。
  优化后 GEMV 有效权重流量 = 28.63 MB / 1.994 s ≈ **14.4 MB/s**，仅为带宽下界的 ~16%
  → 瓶颈仍是 GEMV 指令流，不是 PSRAM 带宽。

## 6b. mixed 可行性（2026-11-06 实测，重要）

- mixed（30,401,920 B）**在设备上成功启动并推理**：
  - bench：**2,017 ms/token（0.496 tok/s）**，gemv 1,860 ms/token，r=0.922（lm_head 未计入口径）；
  - CE（windowed）：待 ppl3 完成；
- 结论：**“q3e4 是唯一可行配置”不成立**——mixed 同时满足容量+精度，且 **CE 更低、速度更快**；
  - mixed 唯一劣势：KV 后 PSRAM 余量 ~0.58 MB（q3e4 ~2.35 MB，约 4×）；
  - 论文口径必须改为：**可行前沿上有 mixed 与 q3e4 两个点；q3e4 作为部署点是因为保留 4× 运行余量**（heap 碎片、USB host、协议栈、未来上下文增长的边界），不是唯一可行；
  - 若审稿人追问“为什么不用 mixed”，答案就是 headroom 的鲁棒性论证；也可补充“standalone 完整固件下 mixed 未验证”。
- 另：mixed 比 q3e4 更快（2,017 vs 2,152 ms/token），说明 q4 attention 的解包比 q3 更便宜；这一点可以作为“位宽分配与 kernel 成本的耦合”讨论素材。

## 8. KV cache FP16 → 192 token（2026-11-06 01:2x 实测）

- 改动：K/V cache 由 FP32 改为 FP16 存储（dense decode 读写时转换），上下文 96→**192 token**，KV 占用保持 **2,359,296 B**（192×2×... ×2B）；
- 版本：`fw_measure_kvfp16.bin`；启动日志 `KV ctx=192 tokens`；
- **CE（windowed 96-token）**：window0 = **6.660667** vs FP32-KV 的 6.662094 → **ΔCE = 0.00143（0.02%）**，可忽略；
- **速度**：2,153.9 / 2,154.3 ms/token（r=0.984）——与 96-token FP32 版本（2,152）差异在噪声内；
- 结论：KV FP16 让同一 PSRAM 预算下上下文翻倍，代价可忽略；论文可把部署上下文从 96 升级为 **192 token**（Table I KV 行：192 tok, FP16, 2,359,296 B）。
- 注意：stream 版 decode 函数仍按 FP32 KV 写（未被固件调用）；dense 路径已全部改为 FP16。

## 8b. 192-token 上下文收益（2026-11-06 02:0x 实测）

- `/pplw 192`：单窗口 192 token（191 个 CE 目标）→ **CE 5.970078，PPL 391.5**；
- 同前缀按 96-token 重置（前两个 96 窗口，190 目标）→ 加权 mean **7.0135（PPL ~1,107）**；
- 结论：**上下文从 96→192 使 CE 下降 ~15%**（5.97 vs 7.01），PPL 从 ~1107 降到 392；
  这证明 192 token 的上下文不仅在内存上可行，而且有可测量的建模收益；
- 注意两组的 CE 目标集合略有差异（191 vs 190 个目标，差 token 96）。

## 10. 逐 token 延迟分布（2026-11-06 12:5x 实测）

- 40 个 token（两次 bench：8 + 32，位置 0–39）：
  - **mean 2,166.6 ms**，median 2,164.4 ms，**p50 2,164.9 ms**，**p95 2,189.0 ms**，
    min 2,147.8 ms，max 2,190.7 ms，stdev 13.1 ms；
- 位置效应：从 pos 0 到 pos 31，单 token 延迟从 2,147.8 增至 2,190.7 ms（+2.0%），
  原因是 attention 随 KV 增长而变慢；外推 192 上下文约 +12%（未直接测）。
- 结论：延迟分布窄（std ~0.6%），无长尾；论文可写 “p95 within 2% of median”。

## 12. 测量边界与重复次数（T1.7 记录规范）

- **bench（速度/r）**：`/bench N` 连续 decode N 个 token（token=1，**不含 prefill**），含一次完整 KV pass；同一 build 重复 2–4 次，r 稳定在 0.984–0.986；报告值取每次运行均值。
- **ppl（CE）**：windowed 96-token 窗口独立 reset，窗口间不共享上下文（匹配部署单轮）；q3e4 设备/主机对拍 3 窗口；q2 3 窗口；mixed 3 窗口。
- **规则评分**：greedy、max_new 32；host 同 recipe 全配置，设备端 q3e4（22/30）与 q2（0/30）作交叉验证。
- **/bw**：1 MB PSRAM 顺序读，4 累加器，95.9 MB/s（下界）。
- **不含**：显示刷新、USB 协议栈、音频、Wi-Fi；设备测量时主机仅供电/抓串口，不参与推理。
- **文件**：raw 日志在 `logs/`，汇总 CSV/JSON 在 `paper/measurements/`；每个配置文件 SHA256 记录在仓库 release/README。
